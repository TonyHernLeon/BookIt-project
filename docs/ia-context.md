- Monorepo: `catalog-service/` (Maven, artifactId `catalog-service`, paquete base `com.bookit.catalog`), `docker-compose.yml` en la raíz, `docs/adr/`, `docs/prompts/` (biblioteca de prompts), `docs/comandos.md` (chuleta del alumno), `docs/ia-context.md` (este documento), `docs/arc-hexagonal-esquema.md` (diagrama Mermaid), `docs/modelo-dominio-catalogo.md`.

- Sin Lombok: `record` para DTOs y objetos de valor. `application.yml`, no `.properties`. `open-in-view: false`. Migraciones Flyway inmutables (los cambios van en una V nueva).
- BD: PostgreSQL 16 (`postgres:16`, nunca `latest`), una BD y un usuario por servicio, volumen con nombre `<servicio>-db-data`, servicio Compose `<servicio>-db`. Catálogo: BD/usuario/contraseña `catalog`, host 5433 -> contenedor 5432 (reservas será 5434). Convención: columna `fecha_creacion TIMESTAMPTZ`. Tabla `negocio` (V1): id UUID PK, nombre VARCHAR(150) NOT NULL con CHECK no vacío, categoria VARCHAR(50), ciudad VARCHAR(100), fecha_creacion, índice (ciudad, categoria).
- Git: ramas `feature/BOOK-00X-descripcion` (actual: `feature/BOOK-003-catalog-domain`), commits `tipo: descripción` (feat, fix, docs, refactor, test, chore), `git add .` siempre desde la raíz, un solo PR a `develop` al terminar cada ticket. Autenticación HTTPS con token. `main` recibe de `develop` al cerrar una fase (ADR 0008).
- Para `mvn clean verify` hace falta Docker Desktop abierto y `docker compose up -d` (el test de contexto de Spring usa la BD). Los tests de dominio y servicio NO necesitan Docker.

## Decisiones ya tomadas (no cambiar sin proponer un ADR nuevo)
0001 monorepo; 0002 PostgreSQL 16 flotante `postgres:16`; 0003 una BD por servicio; 0004 volumen con nombre y puerto por BD; 0005 Flyway dueño del esquema, Hibernate `ddl-auto: validate`; 0006 UUID generado por la aplicación; 0007 JAR ejecutable; 0008 rama `develop` como integración; 0009 `Negocio` entidad que nace válida; 0010 `Categoria` y `Ciudad` records con `strip()`; 0011 fecha recibida desde fuera con `Clock`; 0012 nombre `String` validado en `Negocio`; 0013 puertos del catálogo; 0014 excepciones de dominio.
Detalles de diseño vigentes:
- `Negocio`: constructor privado; `crear(nombre, categoria, ciudad, fechaCreacion)` genera el UUID; `reconstruir(id, nombre, categoria, ciudad, fechaCreacion)` recibe id y fecha; sin setters; `equals`/`hashCode` solo por `id`; nombre normalizado con `strip()` en un único método privado (no nulo, no vacío, máx 150). `id`, `fechaCreacion` y `comando` nulos lanzan `NullPointerException` (Objects.requireNonNull): son errores de programación; los datos del usuario lanzan excepciones de dominio.
- `Categoria` (máx 50) y `Ciudad` (máx 100): records, constructor compacto: null -> excepción, `strip()`, `isEmpty()` o longitud -> excepción. Constante pública `MENSAJE_INVALIDA` con el mensaje.
- Excepciones, todas unchecked: `DominioException` (abstract, constructor protected) -> `DatoInvalidoException` (abstract) -> `NombreNoValidoException`, `CategoriaNoValidaException`, `CiudadNoValidaException`; y `NegocioNoEncontradoException` cuelga de `DominioException`. Una por campo. Los mensajes son para desarrolladores; la capa web traducirá por tipo (400/404) en otro ticket.
- Puertos de entrada (una interfaz por caso de uso, `application.port.in`): `RegistrarNegocioUseCase.registrar(RegistrarNegocioCommand)` (el command es un record con `nombre`, `categoria`, `ciudad` como String, sin validar), `ConsultarNegocioUseCase.consultarPorId(UUID)` (devuelve `Negocio`; si no existe, excepción), `BuscarNegociosUseCase.buscar(Ciudad, Categoria)` (devuelve `List<Negocio>`, vacía si no hay). Asimetría conocida y documentada: `registrar` recibe String y `buscar` recibe los records ya construidos.
- Puerto de salida (`application.port.out`): `NegocioRepository` con `guardar(Negocio)`, `buscarPorId(UUID)` -> `Optional<Negocio>`, `buscarPorCiudadYCategoria(Ciudad, Categoria)` -> `List<Negocio>`. El nombre definitivo es `buscarPorId` (no `obtenerPorId`).
- `NegocioService` (`application.service`, Java puro, sin anotaciones de Spring): implementa las tres interfaces; recibe `NegocioRepository` y `Clock` por constructor; `registrar` hace requireNonNull del comando, construye `Categoria` y `Ciudad`, llama a `Negocio.crear(..., clock.instant())` y devuelve lo que devuelve `guardar`; `consultarPorId` usa `orElseThrow` con `NegocioNoEncontradoException("No existe ningún negocio con ID: " + id)`; `buscar` valida nulos y delega.
- Aplazado y documentado como evolución: categorías y ciudades como tablas propias (V2), país en `Ciudad`, regla de nombres solo numéricos, UUID v7.

## Formatos obligatorios
- ADR: `# 00NN. Título`, `Fecha: AAAA-MM-DD`, `Estado: Aceptada`, secciones `## Contexto` (hechos), `## Decisión` (presente, concreta), `## Alternativas consideradas` (con el porqué del descarte), `## Consecuencias` (Positivas, Negativas, Obligaciones). Sin emojis, línea en blanco bajo cada encabezado, un ADR por decisión; los detalles que concretan se añaden al mismo ADR y los cambios de fondo van en un ADR nuevo. Fichero `NNNN-titulo-en-minusculas.md` y enlace en el índice del README raíz con nombre idéntico.
- Biblioteca de prompts (`docs/prompts/000N-nombre.md`): Objetivo, Prompt, Resultado, Qué tuve que corregir, Lección. Cada prompt que genere código debe pedir: ruta y paquete exactos, ficheros permitidos, "no toques nada más", prohibir imports de frameworks en domain/application, sin Lombok, sin comentarios innecesarios, nombres exactos de constantes, fechas fijas en tests (nunca Instant.now()), salto de línea final.
- Cierre de sub-issue: Qué he investigado/construido, respuestas a las preguntas, decisiones, correcciones durante la revisión, qué he aprendido, comprobaciones, entregables, criterio de hecho.
- Chuleta `docs/comandos.md`: tablas "Para qué / Dónde / Comando" y "Cuando algo falla" (Síntoma / Causa / Qué hago). Cuando el alumno se atasque con algo nuevo, ofrece la fila.
